# 0009 — build123d comme noyau de CAO paramétrique

Date : 2026-09-28
Statut : acceptée

> **Manquement de procédure signalé.** Fiche écrite *après* installation,
> ce que la règle 5 interdit. Consigné plutôt que tu.

## Contexte

La phase 1 étape B demande de dessiner des pièces. Il faut un noyau de
CAO paramétrique pilotable en Python, puisque la règle 1 impose que toute
cote structurelle dérive de `H` et d'un ratio — donc soit calculée, jamais
saisie.

## Options examinées

| Option | Écartée pour |
| --- | --- |
| FreeCAD en script | Interface Python liée à l'application, difficile à exécuter sans affichage et à figer en version |
| OpenSCAD | Langage propre, pas Python ; pas de STEP natif, et l'export DXF y est indirect |
| CadQuery | Voir ci-dessous |
| **build123d** | Retenue |

### build123d plutôt que CadQuery

Les deux s'appuient sur **le même noyau géométrique**, OCCT, via le même
binding OCP. Le choix ne porte donc pas sur les capacités géométriques,
qui sont identiques, mais sur l'ergonomie et la trajectoire du projet :

- **build123d est l'évolution directe de CadQuery**, écrite par des
  contributeurs de CadQuery pour lever ses limites d'API. Il offre deux
  styles — *builder* (contextes `with`) et *algebra* (opérateurs sur les
  formes) — là où CadQuery impose son chaînage fluide.
- Le chaînage de CadQuery s'accommode mal du **code paramétrique long**,
  celui où une cote naît d'un calcul et non d'un littéral. C'est
  exactement notre cas : règle 1.
- build123d expose directement les **objets topologiques** (faces, arêtes,
  sommets), ce qui rend les vérifications automatiques possibles — et le
  projet en dépend : rien n'est présenté comme correct sans contrôle.
- L'export **DXF** est de première classe (`ExportDXF`, via `ezdxf`), avec
  l'unité déclarée explicitement. Vérifié, voir ci-dessous.

Ce n'est pas un jugement de valeur sur CadQuery, qui reste maintenu.

## Décision

### 1. Version épinglée strictement

```
build123d==0.13.0
```

Résolue **par pip le 2026-09-28** sur Python 3.14.4, pas imposée a
priori. Noyau : `cadquery-ocp-novtk 8.0.1.0.0`, soit **OCCT 8.0.1**.

**Motif de l'épinglage strict.** OCCT est un noyau géométrique C++. Une
montée de version peut modifier une tolérance de booléen, un arrondi ou
une tessellation **sans lever la moindre erreur** : la pièce sort
différente, et rien ne le signale. C'est exactement le mode de défaillance
déjà rencontré deux fois sur ce projet — les butées moteur prises pour
des butées d'articulation, et la pose de référence de la politique de
marche. Un faux silencieux.

Les 56 dépendances résolues sont notées dans `requirements.txt`.

### 2. Chaîne d'export vérifiée, pas supposée

`scripts/check_cad_toolchain.py`, **16 contrôles, 16 passés** sur une
pièce d'essai 40 × 20 × 5 mm percée Ø6 :

| Format | Contrôle | Résultat |
| --- | --- | --- |
| STEP | entité `LENGTH_UNIT = SI_UNIT(.MILLI.,.METRE.)` | conforme |
| STEP | relu, cotes 40 / 20 / 5 mm | conforme |
| STL | étendue des sommets 40 / 20 / 5 | conforme |
| **DXF** | **`$INSUNITS = 4`** (millimètres) | **conforme** |
| **DXF** | étendue du contour 40 × 20, perçage Ø6,0000 | **conforme** |

Le DXF conditionne toute la chaîne de découpe 2D, et CLAUDE.md exige
« millimètres, échelle 1:1 ». Un facteur d'échelle erroné ne lève aucune
erreur : il envoie une pièce au centimètre chez le découpeur. La
vérification est donc mesurée, et rejouable à chaque montée de version.

### 3. Licences

Vérifiées sur les 56 paquets installés : Apache-2.0, MIT, BSD, PSF,
ISC. **Ni GPL ni CERN-OHL-S** — la règle de CLAUDE.md est respectée.

**Point de vigilance non résolu** : OCCT, le noyau C++ sous-jacent, est
publié par Open CASCADE sous LGPL-2.1 avec exception. Le paquet
`cadquery-ocp-novtk` déclare Apache-2.0 pour son propre code et
**n'embarque pas le texte de licence d'OCCT** : je n'ai pas pu vérifier
cette information depuis l'environnement. LGPL n'est ni GPL ni
CERN-OHL-S, donc la règle n'est pas enfreinte telle qu'elle est écrite,
mais le point mérite d'être tranché avant toute exploitation
commerciale — au même titre que la licence des poids (fiche 0003) et
celle des fichiers mécaniques amont (fiche 0001).

## Conséquences

- Monter `build123d` ou OCCT est une **décision**, pas une routine : elle
  impose de rejouer `scripts/check_cad_toolchain.py` et de comparer les
  pièces produites avant/après.
- La règle 1 devient applicable : les cotes se calculent depuis
  `params/anthropometry.yaml`, elles ne se saisissent plus.
- `build123d` vit dans le venv **du projet** (3.14). Aucun lien avec le
  venv amont : la règle des deux interpréteurs est intacte.
